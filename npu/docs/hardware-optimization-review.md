# 硬件优化检查：6697d58

本次检查 RTL、实际固件和已有报告，没有修改 RTL 或固件，也没有重跑综合/PNR。性能来自当前源码 SHA 全部匹配的 `vcs-syncobs_v2-blocking-macro`，10 张图均为 23,937 周期；下表使用 sample0 的逐层统计。原始提取与核对结果在 [hardware-optimization-review.json](../reports/hardware-optimization-review.json)。

面积参考 edbb4ce 的 18ns 门控、保留单元边界综合：2.547215mm²，包含两块 SRAM，不含 PAD/CTS/布线。该版本早于新增 SYNC 观测寄存器，不能作为当前面积。面积收益和周期收益均需实现后测量，以下不作保证。

## 1. 首先利用已有硬件，合并 FC 的 K 任务

`firmware.py:397` 仍设置 K=16，每个 1×4 / 1×4 / 1×2 输出块提交九次；硬件现在支持 K≤256。默认 FC 是27个原始 GEMM任务，加10个 K=0 量化导出，共37个任务。

优先对照 K=144，每个输出块一次：原始 GEMM变3个，加量化导出共13个。无需增加硬件。已有权重是单份转置布局、ldb=144，能够表达长K；需要验证边界、INT32模累加、量化参数切换及输出一致性。

原始分段计算目前写回90个部分和，并在后续段读回80个部分和；合并后对应10次最终写、不再为K分段读回。10个 K=0 量化导出仍需读10个最终值。因供数和CPU提交会重叠，不能据任务数比例预测加速。

这也说明：扩大硬件能力后，应先检查固件有没有仍按旧上限拆任务。

## 2. Matrix/Vector 供数：消除协议空拍

`npu_multi_read.sv:51` 用 `!pending` 阻止下一普通读。当前单周期应答下，发出一读后必须先等应答，下一请求还要再下一拍发出，普通口最多每两拍一读，即使 SRAM 每拍可接受请求。批次也只能有一个，结果接收、调用者写入 word staging、返回 FETCH 之间仍有控制周期。

建议先做最小改进：应答返回同拍允许下一读接管 pending/owner；错误时先阻止后续请求，已获 grant 的请求必须排干。之后评估 response forwarding 和一组小的下一K操作数缓冲，避免大幅增加状态机。

现有实现每个计算单元只有一路普通访存请求；XBAR虽有两块独立 SRAM，不能替同一个单元凭空产生第二路地址。仅优化仲裁不会让它自动得到2×32bit吞吐。两路普通请求会扩大端口、返回标签和冲突处理，优先级应低于先消除现有接口空拍。

Matrix 已有同字复用和最多三个 RF gather 槽；不能把它描述成每个元素都重新访存，也不能认为三个 gather 槽足以同时供齐4个A和4个B。默认 FC M=1，4×4阵列的另三行本来就空闲，算术阵列扩容不是首选。

## 3. 共享量化：将吞吐与写回解耦

QT01 当前是 state0采样乘积→state1加偏置→state2等待输出，然后回state0。即使下游始终就绪，全局也最多每3拍接收一个结果，CNN/Matrix共享这个接收能力；它不是每拍接收的流水线。

本次量化 active=3,798拍，其中输出有效但下游未就绪仅210拍。不能把全部 CNN 输出反压都归因于写口。建议先评估两级弹性流水或小结果缓冲，使旧结果等待写回时能处理下一结果。

注意当前生产者一直保持原结果，到量化输出消费才收到 ready。若改为早接收，CNN output_position/output_final、Matrix输出位置等元数据也必须随结果保存，不能只加一个数值寄存器。这些是小的数据/标签缓冲，不是新的模型描述符执行器。还应保留当前参数采样、flush和可选INT32旁路语义。

## 4. INT8 连续写回合并

CNN/Matrix量化打包模式当前只是选择byte enable，每个INT8结果仍单独获得一次写grant和应答。可以在写回侧加32bit组装寄存器、字地址、byte-valid和对应结果计数，合并同一目标字的连续byte。

默认前三层共有1,568个最终SRAM字节。若按连续地址理想合并，对应写事务可由1,568降到392；这是事务数上限分析，不是整体周期可缩短四倍。后两层RF最终输出216B，也可评估类似合并。

非连续地址、目标/pack/enable实时修改、任务尾部和flush都必须使组装器正确结算。流FIFO原有“一次写入一个token”语义不能被合并改变。多个结果共一个应答时，新的WRITTEN/WRITE_ERRORS要按结果数还是事务数计数也必须明确；不能静默破坏软件同步契约。

## 5. CNN：供数优先于增加MAC，现有预取不要重复实现

CNN已有3行×3word环形窗口、逐行在途请求、到达应答直接旁路给MAC、下一输入通道权重预取。这些不是待补功能。

剩余输入等待主要在Conv3/4：2,384/1,040拍。值得评估跨任务保留权重或下一窗口准备，但共享配置允许软件随时改写，不能假定下一任务使用同一src/kernel/stride；复用必须有明确匹配条件或由软件显式请求。重载权重/窗口也可能是任务切换必需，不能直接删。

当前部分和读RF共3,472次，部分和等待664拍；RF独立写口等待仅56拍，CNN gather冲突仅32拍。因而单纯增加RF端口不像主要突破口。保留共享RF思路，先优化布局与调度；不建议为减少这664拍立即引入一大块CNN私有缓存。

## 6. Vector：值得优先处理的时序问题

历史18ns综合最差路径从 Vector program PC，经程序选择/操作数选择、乘法与结果组合逻辑，到 Vector临时寄存器；slack约+0.0017ns，几乎没有综合裕量。另有QT01移位/裁剪到SRAM数据脚的接近临界路径。

建议在宽乘法路径增加明确的操作数/结果级，或把INT32乘法及MULH类实现为多周期；简单操作和SIMD8尽量维持短路径。当前默认推理不使用Vector，因此这种改动可能改善频率/映射面积而不增加该负载周期；通用Vector负载必须另测，不能将默认推理不变理解为无代价。

Vector程序表是执行时实时读取。增加指令预取/译码寄存器会改变程序表修改的采样时点，需要更新软件契约和定向测试。保留MULH/MULHU等通用功能，不建议直接删掉来换面积。

Vector访存也有A_REQ/A_WAIT/D_REQ/D_WAIT串行阶段；即便四路INT8 ALU，每拍四元素仍不是端到端吞吐保证。后续同样可以用小操作数/写回缓冲重叠处理。

## 7. 面积：存储组织通常比继续改仲裁更值得看

历史保留边界综合中，XBAR约0.3640mm²、Matrix约0.3512、MMIO/任务队列约0.2268、CNN约0.2096。较早可归属leaf报告显示XBAR内部RF与流FIFO占近90%；最新综合的嵌套来源前缀不完整，不能将工具导出的RF/FIFO=0视为真实零面积。

最新历史MMIO leaf中，DF/SDF单元约0.13964mm²，占该模块约61.6%；组合逻辑约0.08482mm²，门控约0.00231mm²。任务队列、程序表、shadow/active配置和诊断寄存器都在这一模块内，不能把它全部叫队列开销。

可以分别扫描任务队列深度和四条流FIFO深度。当前默认推理不用单元间流FIFO，但通用转发测试需要；可尝试流FIFO16→8或4，保留参数化能力。CNN/Matrix/Vector任务FIFO当前8/8/8，不能将两类FIFO混淆。当前已有队列空间轮询，不建议盲目把任务队列全部减半。

另外，lda/ldb写入限制≤4096，但shadow及跨度算术声明为32bit。可显式收窄为13bit间距和足宽跨度/越界判定，检查是否减少乘加和比较逻辑。不能直接截断所有32bit CSR：有些非法字段目前在START才报错，截断可能把非法值变成合法任务。综合可能已经消除部分冗余，收益需网表证明。

## 优先顺序与验证

1. 软件：FC K144、减少重复配置/状态读取；硬件不变做周期对照。
2. 小硬件：普通读应答同拍续发、减少batch往返空拍。
3. 性能：QT01弹性处理与连续INT8合并写回，分别测量后再组合。
4. 时序：Vector宽乘法切分；检查QT01到SRAM写数据路径。
5. 面积：流FIFO深度扫描、CSR/跨度位宽梳理，最后再考虑RF容量变化。

每项单独测默认MNIST、随机GEMM/Vector、stride1/2和非对齐卷积、RF/SRAM/FIFO背压、flush/错误恢复，以及SYNC计数。面积/频率使用同一18ns门控综合约束；选定候选后才跑完整含PAD布局布线。当前数据不能承诺任何一项单独或组合必达20k周期。
